🛡️ 4. หมัดเด็ด! สาธิตความปลอดภัยและการทดสอบเชิงลบ (Negative Testing)

ถ้าอาจารย์เริ่มถามว่า "ระบบนี้ปลอดภัยแค่ไหน? มีช่องโหว่ไหม?" ให้ทำ 3 ข้อนี้โชว์ทันที:

1. ทดสอบการปฏิเสธ HTTP GET บนเส้นทางที่อันตราย (HTTP 405 Method Not Allowed)

ลองพิมพ์ URL http://127.0.0.1:8000/cart/add/ หรือ http://127.0.0.1:8000/staff/logout/ ลงใน Address Bar ตรง ๆ

ผลลัพธ์ที่ระบบตอบสนอง: เซิร์ฟเวอร์จะตอบกลับด้วยรหัส 405 Method Not Allowed ทันที! อธิบายอาจารย์ว่า: "ระบบถูกออกแบบตามหลัก OWASP ป้องกันการโจมตีแบบ CSRF และป้องกันเว็บเบราว์เซอร์หรือ Web Crawler แอบยิงคำสั่งเปลี่ยนข้อมูลผ่านคำขอ GET"

2. ทดสอบการควบคุมสิทธิ์ตามบทบาท (Role-Based Access Control - RBAC)

ในหน้าต่างเบราว์เซอร์ของลูกค้าทั่วไป (ล็อกอินด้วยบัญชี ohm) ลองพิมพ์ URL โซนเจ้าหน้าที่ เช่น http://127.0.0.1:8000/employees/ หรือ /orders/

ผลลัพธ์ที่ระบบตอบสนอง: ระบบจะตรวจพบว่าไม่ใช่ Staff และดีด (Redirect) กลับมาที่หน้าล็อกอินเจ้าหน้าที่ทันที ไม่เปิดเผยข้อมูลพนักงานหรือออเดอร์ให้คนนอกเห็น

3. โชว์ผลการรันชุดทดสอบอัตโนมัติ (Automated Unit Tests)

เปิดหน้าต่าง Terminal แล้วรันชุดทดสอบเพื่อโชว์ความสมบูรณ์แบบของโค้ด: 

python manage.py test myapp
ผลลัพธ์: Ran 412 tests in ~35s ... OK (ผ่าน 100% ครบทุกโมเดล, ทุกวิว, ทุกเซอร์วิส และทุกเทมเพลต)

💡 5. แนวคำถามที่อาจารย์น่าจะถาม & บทตอบแบบวิชาการ (Q&A Defense)

คลิกที่คำถามเพื่อดูแนวทางการตอบที่ถูกต้องตามหลักวิศวกรรมซอฟต์แวร์:

❓ 1. ทำไมถึงไม่ให้เจ้าหน้าที่กดเปลี่ยนสถานะเป็น "ชำระเงินแล้ว" ด้วยตัวเอง? ▼
"ตอบ: เพราะระบบของเรายึดหลัก Single Point of Payment Entry ครับอาจารย์ ในระบบพาณิชย์อิเล็กทรอนิกส์ การที่เจ้าหน้าที่สามารถกดเปลี่ยนสถานะเงินได้ตามใจชอบคือช่องโหว่ร้ายแรงที่ทำให้เกิดการทุจริตและหนี้สูญ ระบบของเราจึงบังคับว่าสถานะ 'ชำระเงินแล้ว' จะเกิดขึ้นได้ต่อเมื่อมีประวัติการชำระเงินจริงในตาราง Payment ผ่านฟังก์ชัน PaymentService.record_payment() และมียอดเงินสะสมครบตามราคาสินค้าเท่านั้นครับ"
💡 เสริมถ้าอาจารย์ถามต่อ: แล้วถ้าเงินสดมาหน้าร้านล่ะ? -> ตอบว่า "เรามีระบบ Superuser Override สำหรับผู้ดูแลระบบสูงสุดเท่านั้น ที่สามารถบันทึกเงินสดพร้อมระบุเหตุผลในการตรวจสอบย้อนหลังได้ครับ"
❓ 2. ทำไมขั้นตอนสุดท้าย "ถึงมือแล้ว" ถึงต้องให้ลูกค้ายืนยันเอง ไม่ให้เจ้าหน้าที่เป็นคนกด? ▼
"ตอบ: ตามหลักการ Proof of Delivery และ Two-Party Consensus ครับ ของจะถือว่าถึงมืออย่างสมบูรณ์ก็ต่อเมื่อผู้รับยืนยันว่าได้รับของแล้ว ไม่ใช่ผู้ส่งทึกทักเอาเองว่าส่งสำเร็จ การให้ลูกค้ายืนยันเองช่วยลดข้อพิพาทเรื่องพัสดุสูญหายได้อย่างเด็ดขาดครับ"
💡 เสริมถ้าอาจารย์ถามต่อ: แล้วถ้าลูกค้าไม่ยอมกดยืนยันล่ะ? -> ตอบว่า "ในหน้าเจ้าหน้าที่มีปุ่มสำรองสำหรับกรณีฉุกเฉิน (เช่น ติดต่อลูกค้าไม่ได้ หรือสินค้าเป็นแบบเก็บเงินปลายทาง COD) แต่ระบบจะติดป้ายเตือนว่าเป็นทางเลือกสำรองและบันทึกประวัติการกดไว้ใน Audit Log ครับ"
❓ 3. การออกแบบฐานข้อมูลนี้เป็นแบบบรรทัดฐานขั้นที่ 3 (3NF) หรือไม่ อย่างไร? ▼
"ตอบ: เป็น 3NF (Third Normal Form) อย่างสมบูรณ์ครับอาจารย์:
  • 1NF: ทุกคอลัมน์เก็บค่าเชิงอะตอม (Atomic Value) ไม่มีค่าซ้ำซ้อนในฟิลด์เดียว
  • 2NF: ทุกคอลัมน์ที่ไม่ได้เป็นคีย์ ขึ้นตรงกับ Primary Key หลักอย่างสมบูรณ์ เช่น แยก OrderItem ออกมาเพื่อเก็บรายการสินค้าแต่ละแถว
  • 3NF: กำจัด Transitive Dependency ทั้งหมด ที่สำคัญคือเราแยก OrderItem.price ไว้เก็บราคา ณ วันที่ซื้อ (Price Snapshot) ต่างหากจาก Product.price ทำให้เวลาปรับราคาสินค้าในปัจจุบัน จะไม่กระทบต่อประวัติยอดขายและรายงานการเงินย้อนหลังครับ"
❓ 4. สถาปัตยกรรมแบบ 4 ชั้น (Clean 4-Layer) ในระบบนี้ทำงานอย่างไร? ▼
"ตอบ: เราแบ่งออกเป็น 4 ชั้นชัดเจนครับ:
  1. Presentation Layer: เทมเพลต HTML/CSS และ JavaScript ที่รองรับการเคลื่อนไหวแบบ Apple Liquid Glass
  2. Controller Layer: Class-Based Views (CBV) ใน views.py ทำหน้าที่รับคำขอ ตรวจสอบสิทธิ์ (StaffRequiredMixin) และส่งต่อข้อมูล โดยไม่มี Business Logic อยู่ใน View เลย
  3. Service Layer: รวมตรรกะทางธุรกิจ 17 คลาสใน services.py เช่น Cart, PaymentService, OrderStatusService, SlipOK, RateLimit เพื่อความสามารถในการทดสอบซ้ำ
  4. Domain & Model Layer: 9 โมเดลใน models.py ควบคุมความสมบูรณ์ของข้อมูลและนโยบาย Foreign Key ครับ"
❓ 5. ทำไมระบบถึงไม่ใช้ CDN ภายนอก (เช่น cdn.jsdelivr.net สำหรับ Bootstrap)? ▼
"ตอบ: เราออกแบบด้วยปรัชญา Local-First & Zero External CDN Dependency ครับอาจารย์ เพื่อความมั่นคงปลอดภัย (Security), ความเป็นส่วนตัวของลูกค้า (Privacy), และเสถียรภาพในการทำงาน แม้เซิร์ฟเวอร์จะออฟไลน์หรือเน็ตภายนอกมีปัญหา เว็บไซต์ก็ยังสามารถเรนเดอร์ได้ 100% เต็มรูปแบบ ไม่พัง ไม่กระตุก และไม่มีปัญหา Single Point of Failure จาก CDN ภายนอกครับ"
❓ 6. ตารางบันทึกประวัติ `ActivityLog` ออกแบบอย่างไรเพื่อความโปร่งใส? ▼
"ตอบ: ออกแบบเป็น Append-Only Audit Trail ครับ อนุญาตให้กระทำเฉพาะคำสั่ง INSERT เพิ่มเรคคอร์ดใหม่เท่านั้น ไม่อนุญาตให้แก้ไข (UPDATE) หรือลบ (DELETE) ทุกการกระทำที่สำคัญ เช่น การชำระเงิน การเปลี่ยนสถานะออเดอร์ หรือการเข้าสู่ระบบ จะถูกบันทึกพร้อมวันเวลา ผู้กระทำ และรายละเอียดการเปลี่ยนแปลง เพื่อใช้เป็นหลักฐานทางนิติวิทยาศาสตร์คอมพิวเตอร์ (Computer Forensics) ได้ครับ"
