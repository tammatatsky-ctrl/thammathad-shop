## 2. การติดตั้งและเริ่มต้นใช้งาน

### 2.1 ข้อกำหนดของระบบ
* **Python**: 3.12 ขึ้นไป (ทดสอบบน Python 3.14)
* **ฐานข้อมูล**: SQLite (ติดมากับตัวโปรเจกต์พร้อมไฟล์ `db.sqlite3`)

### 2.2 ขั้นตอนเริ่มใช้งานแบบรวดเร็ว (Quick Start)

เปิดโปรแกรม Terminal หรือ PowerShell ในโฟลเดอร์โปรเจกต์ (`d:\django_project\my_django_app`):

```bash
# 1. สร้างและเปิดใช้งาน Virtual Environment
python -m venv .venv
.venv\Scripts\activate           # บน Windows

# 2. ติดตั้งแพ็กเกจที่จำเป็น
pip install -r requirements.txt

# 3. อัปเดตโครงสร้างฐานข้อมูล
python manage.py migrate

# 4. รีเซ็ตข้อมูลตัวอย่างให้สมบูรณ์ (สินค้า 12 ชิ้น, พนักงาน 13 คน, ลูกค้า 6 คน, ออเดอร์ 10 ใบ)
python manage.py seed_catalog
python manage.py seed_demo_data

# 5. รันเซิร์ฟเวอร์
python manage.py runserver
```

### 2.3 ทางเข้าใช้งานระบบ (Key URLs)

* **เอกสาร REST API (Swagger UI)**: [http://127.0.0.1:8000/api/docs/](http://127.0.0.1:8000/api/docs/) *(เฉพาะ Staff)*
* **Django Admin**: [http://127.0.0.1:8000/admin/](http://127.0.0.1:8000/admin/) *(เฉพาะ Superuser)*

## 3. คู่มือการใช้งานทีละขั้นตอน

### 3.1 ฝั่งลูกค้า (Customer Journey)

```
[เลือกสินค้า] ──► [ใส่ตะกร้า] ──► [สั่งซื้อ/กรอกที่อยู่] ──► [ชำระเงิน] ──► [รอจัดส่ง] ──► [ลูกค้ายืนยันรับของ]
```

#### ขั้นตอนที่ 1: เลือกดูและค้นหาสินค้า
1. เข้าไปที่ [http://127.0.0.1:8000/](http://127.0.0.1:8000/)
2. พิมพ์คำค้นหาในช่องค้นหา (เช่น "คีย์บอร์ด", "เมาส์", "จอ") ระบบจะแสดงผลแบบสดทันที (Live Search)
3. คลิกปุ่มกรองหมวดหมู่ด้านบน เพื่อดูสินค้าเฉพาะกลุ่ม เช่น คอมพิวเตอร์ประกอบ, จอภาพ, อุปกรณ์เกมมิง

#### ขั้นตอนที่ 2: สั่งซื้อสินค้าลงตะกร้า
1. กดปุ่ม **"เพิ่มลงตะกร้า"** ที่การ์ดสินค้า
2. คลิกไอคอน **ตะกร้าสินค้า (🛒)** ที่แถบเมนูด้านบน เพื่อปรับจำนวนสินค้า หรือลบรายการที่ไม่ต้องการ
3. คลิกปุ่ม **"ดำเนินการสั่งซื้อ"**

#### ขั้นตอนที่ 3: กรอกข้อมูลจัดส่งและยืนยันคำสั่งซื้อ
1. กรอกชื่อผู้รับ เบอร์โทรศัพท์ และที่อยู่จัดส่ง (สำหรับลูกค้าที่ล็อกอิน ระบบจะดึงที่อยู่จากสมุดบันทึกให้อัตโนมัติ)
2. เลือกวิธีชำระเงิน:
   * **พร้อมเพย์ (PromptPay QR)**
   * **โอนเงินผ่านธนาคาร (Bank Transfer)**
   * **เก็บเงินปลายทาง (Cash on Delivery - COD)**
3. กดยืนยันสั่งซื้อ ระบบจะสร้างเลขออเดอร์ขึ้นต้นด้วย `ORD-YYYYMMDD-XXXX`

#### ขั้นตอนที่ 4: ชำระเงิน
1. หน้าจอจะแสดง QR Code พร้อมเพย์ และยอดเงินที่ต้องชำระ
2. เพื่อความสะดวกในการทดสอบ ระบบมีปุ่ม **"จำลองการชำระเงินสำเร็จ (1 คลิก)"** หรือสามารถอัปโหลดภาพสลิปเพื่อทดสอบระบบ SlipOK OCR ได้
3. **เมื่อยอดเงินชำระครบ**: สถานะจะเปลี่ยนจาก **"รอชำระเงิน"** เป็น **"ชำระเงินแล้ว"** โดยอัตโนมัติทันที

#### ขั้นตอนที่ 5: ติดตามสถานะและยืนยันรับสินค้า
1. เข้าเมนู **"ติดตามคำสั่งซื้อ"** (`/order/track/`)
2. กรอก **เลขออเดอร์** และ **เบอร์โทรศัพท์** (เพื่อความปลอดภัย ไม่ต้องล็อกอินก็ดูได้ แต่ต้องรู้เบอร์คู่กัน)
3. เมื่อร้านส่งของแล้ว สถานะจะเป็น **"จัดส่งแล้ว"**
4. เมื่อพัสดุมาถึง ให้ลูกค้ากดปุ่ม **"ยืนยันว่าได้รับสินค้าแล้ว"** สถานะจะเปลี่ยนเป็น **"ถึงมือแล้ว (สมบูรณ์)"**

#### ขั้นตอนที่ 6: การแจ้งปัญหาคำสั่งซื้อ
1. หากสินค้ามีปัญหา เข้าเมนู **"แจ้งปัญหา"** (`/contact/`) หรือคลิกปุ่มจากหน้าติดตามออเดอร์
2. เลือกระดับปัญหา (สินค้าชำรุด, ส่งผิดรุ่น, ได้รับล่าช้า, การเงิน) แล้วระบุรายละเอียด

### 3.2 ฝั่งเจ้าหน้าที่และผู้จัดการ (Staff & Admin Operations)

เข้าสู่ระบบที่ [http://127.0.0.1:8000/staff/login/](http://127.0.0.1:8000/staff/login/) ด้วยบัญชี `teacher` หรือรหัสพนักงาน

#### 1. จัดการคำสั่งซื้อและสถานะพัสดุ (`/orders/`)
* **ดูรายการคำสั่งซื้อ**: คัดกรองตามสถานะ (รอชำระ, ชำระแล้ว, จัดส่งแล้ว, ถึงมือแล้ว)
* **เลื่อนสถานะจัดส่ง**: เมื่อออเดอร์มีสถานะ "ชำระเงินแล้ว" พนักงานบรรจุของเสร็จให้กดปุ่ม **"ปรับเป็น: จัดส่งแล้ว"** พร้อมระบุเลขพัสดุ
* *ข้อควรจำ*: เจ้าหน้าที่กดข้ามขั้นไม่ได้ และกดเปลี่ยนสถานะเป็น "ชำระเงินแล้ว" ด้วยมือไม่ได้ (ต้องมียอดเงินเข้าจริงผ่าน Payment)

#### 2. ตรวจสอบการเงิน (`/payments/`)
* แสดงรายการเงินเข้าทุกบาททุกสตางค์ ทั้งที่มาจากการสแกนสลิป หรือปุ่มทดสอบ
* แสดงประวัติว่าเงินแต่ละก้อนผูกกับออเดอร์ใด วันที่และเวลาเท่าใด

#### 3. จัดการสินค้าและสต็อก (`/product/manage/`)
* เพิ่มสินค้าใหม่ แก้ไขราคา และปรับจำนวนสต็อกคงเหลือ
* มีแถบเตือนสีส้มอัตโนมัติเมื่อสินค้าในสต็อกเหลือน้อยกว่า 5 ชิ้น
* มีปุ่ม AI ช่วยคิดคำอธิบายสินค้าภาษาไทย (Gemini AI) และปุ่มช่วยแปลภาษา (MyMemory)

#### 4. คิวจัดการปัญหา (`/orders/issues/`)
* เจ้าหน้าที่ตรวจสอบข้อร้องเรียนจากลูกค้า
* เมื่อแก้ไขปัญหาเสร็จ ให้กด **"ปิดเรื่อง"**
* **กฎความปลอดภัย**: ระบบจะไม่อนุญาตให้ปิดเรื่องจนกว่าเจ้าหน้าที่จะพิมพ์บันทึก **"ผลการแก้ไขปัญหา (Resolution)"** ลงในระบบ

#### 5. แดชบอร์ดและรายงานยอดขาย (`/dashboard/` และ `/reports/`)
* แสดง KPI สำคัญ: ยอดขายรวม (คำนวณจากเงินที่เข้าจริงใน Payment), จำนวนออเดอร์, สินค้าขายดี 5 อันดับแรก
* กราฟสรุปยอดขายรายวันและรายหมวดหมู่
* ปุ่ม **"ส่งออกรายงานเป็น CSV"** สำหรับนำข้อมูลไปเปิดใน Microsoft Excel

#### 6. ประวัติการทำงานย้อนหลัง Audit Trail (`/reports/audit/`)
* บันทึกทุกเหตุการณ์สำคัญ: ใครเข้าสู่ระบบ, ใครเพิ่มสินค้า, ใครแก้ข้อมูล, ใครเปลี่ยนสถานะออเดอร์
* ระบบบันทึกแบบ **Diffing**: แสดงค่าเดิมเทียบกับค่าใหม่ชัดเจน (เช่น เปลี่ยนสต็อกจาก 10 $\rightarrow$ 8) พร้อมที่อยู่ IP

## 4. คู่มือการทดสอบระบบ

### 4.1 การรันชุดทดสอบอัตโนมัติ

โปรเจกต์มีชุดทดสอบอัตโนมัติครอบคลุมทั้งระบบถึง **383 Test Cases** ทำหน้าที่เป็นตาข่ายนิรภัย (Safety Net):

```bash
# ก) ตรวจความพร้อมด้านความปลอดภัยและระบบ (Preflight Check)
python manage.py preflight

# ข) รันเทสต์แบบเร็ว (ใช้เวลา ~7 วินาที - ตรวจความสมบูรณ์เทมเพลต แดชบอร์ด และ AJAX)
python manage.py test myapp.tests.test_template_hygiene myapp.tests.test_dashboard myapp.tests.test_ajax_convention

# ค) รันเทสต์เอกสารรายงาน PDF/Word (ใช้เวลา ~5 วินาที)
python manage.py test myapp.tests.test_report_docs

# ง) รันชุดทดสอบทั้งหมดครบ 383 กรณีทดสอบ (ใช้เวลา ~1.5 นาที)
python manage.py test myapp
```

### 4.2 สถานการณ์ทดสอบจริงสำหรับตรวจงาน (Manual Test Scenarios)

อาจารย์หรือผู้ตรวจสามารถทดสอบฟังก์ชันสำคัญตาม 6 สถานการณ์จำลองดังนี้:

#### 🧪 สถานการณ์ที่ 1: กฎ "จุดรับเงินจุดเดียว" (Single Point of Entry)
* **จุดประสงค์**: พิสูจน์ว่าเงินทุกช่องทางต้องวิ่งผ่าน `PaymentService` และยอดเงินสะสมควบคุมสถานะออเดอร์
* **ขั้นตอนทดสอบ**:
  1. เข้าหน้าร้าน สั่งซื้อสินค้าชิ้นใดก็ได้ 1 ชิ้น (สมมุติราคารวม 1,200 บาท) เลือกชำระแบบโอนเงิน
  2. เปิดหน้าติดตามออเดอร์ จะเห็นแถบสถานะเป็น `รอชำระเงิน (Pending)`
  3. ไปที่หน้าฝั่งพนักงาน `/orders/` แล้วลองมองหาปุ่มเปลี่ยนสถานะเป็น "ชำระเงินแล้ว" $\rightarrow$ **จะพบว่าไม่มีปุ่มให้เจ้าหน้าที่กดเอง**
  4. กลับมาที่หน้าชำระเงิน ลองกดทดสอบแจ้งยอดเพียงบางส่วน เช่น โอนมา 500 บาท
  5. ระบบจะขึ้นแถบเตือนสีเหลืองว่า *"ชำระแล้ว 500.00 บาท (ยังขาดอีก 700.00 บาท)"* และสถานะยังคงเป็น `รอชำระเงิน`
  6. เมื่อโอนยอดที่เหลืออีก 700 บาทครบ $\rightarrow$ สถานะจะเปลี่ยนเป็น `ชำระเงินแล้ว (Paid)` ทันทีโดยอัตโนมัติ

#### 🧪 สถานการณ์ที่ 2: กฎ "บันไดสถานะทิศทางเดียว ห้ามข้าม ห้ามถอยหลัง"
* **จุดประสงค์**: ป้องกันการทุจริตและการข้ามขั้นตอน
* **ขั้นตอนทดสอบ**:
  1. ออเดอร์ที่ยังไม่ชำระเงิน $\rightarrow$ เจ้าหน้าที่ไม่สามารถกดข้ามไปเป็น "จัดส่งแล้ว" ได้
  2. ออเดอร์ที่ชำระเงินแล้ว $\rightarrow$ เจ้าหน้าที่กดเปลี่ยนได้เพียงสถานะถัดไปขั้นเดียวคือ "จัดส่งแล้ว"
  3. เมื่อสถานะเป็น "จัดส่งแล้ว" $\rightarrow$ ไม่มีปุ่มกดย้อนกลับไปเป็น "รอชำระเงิน" หรือ "ชำระเงินแล้ว" ได้อีก

#### 🧪 สถานการณ์ที่ 3: กฎ "ของถึงมือ ลูกค้าต้องยืนยันเอง"
* **จุดประสงค์**: ของถึงมือก็ต่อเมื่อผู้รับบอกว่าได้รับแล้ว ไม่ใช่ผู้ส่งกดเองฝ่ายเดียว
* **ขั้นตอนทดสอบ**:
  1. เข้าหน้าติดตามออเดอร์ของใบที่สถานะเป็น "จัดส่งแล้ว" ด้วยเลขออเดอร์ + เบอร์โทร
  2. ลูกค้าจะเห็นปุ่มเด่นสีฟ้า **"ยืนยันว่าได้รับสินค้าแล้ว"**
  3. เมื่อลูกค้ากดปุ่มยืนยัน สถานะจะเปลี่ยนเป็น **"ถึงมือแล้ว (Delivered)"** ทันที
  4. ฝั่งเจ้าหน้าที่ในหน้า `/orders/` จะแสดงว่ามีทางเลือกสำรองไว้เฉพาะกรณีฉุกเฉิน (เช่น เก็บเงินปลายทางแล้วติดต่อลูกค้าไม่ได้) พร้อมป้ายเตือนกำกับ

#### 🧪 สถานการณ์ที่ 4: กฎ "ปิดเรื่องร้องเรียนต้องระบุวิธีแก้ปัญหา"
* **จุดประสงค์**: บังคับความรับผิดชอบในการบริการลูกค้า
* **ขั้นตอนทดสอบ**:
  1. เข้าหน้าคิวปัญหา `/orders/issues/`
  2. เลือกเคสปัญหาที่เปิดค้างอยู่ กดปุ่ม "ปิดเรื่อง" โดยปล่อยช่องผลการแก้ไขว่างไว้
  3. ระบบจะปฏิเสธการทำรายการที่ระดับ Service Layer (ไม่ใช่แค่ HTML required) บังคับให้ต้องระบุแนวทางแก้ไขก่อนเสมอ

#### 🧪 สถานการณ์ที่ 5: กฎความปลอดภัย Fail-Closed และการแบ่งสิทธิ์ RBAC
* **จุดประสงค์**: ป้องกันผู้ใช้ทั่วไปแอบเข้าถึงโซนหลังบ้าน
* **ขั้นตอนทดสอบ**:
  1. ใช้เบราว์เซอร์ปกติโดยไม่ล็อกอินพนักงาน แล้วลองพิมพ์เข้า URL ตรงๆ เช่น `http://127.0.0.1:8000/employees/` หรือ `/dashboard/`
  2. ระบบจะ Redirect ไปที่หน้า `/staff/login/` ทันทีด้วย `StaffRequiredMixin`
  3. หากล็อกอินด้วยบัญชีลูกค้าทั่วไป (`wichai.s`) แล้วพยายามเข้าหน้าหลังบ้าน ระบบจะปฏิเสธและเตือนว่าสิทธิ์ไม่เพียงพอ

#### 🧪 สถานการณ์ที่ 6: การจำกัดอัตราคำขอ (Rate Limiting)
* **จุดประสงค์**: ป้องกันการโจมตีแบบ Brute Force หรือการรัวยิงสลิปปลอม
* **ขั้นตอนทดสอบ**:
  1. การขอรับ Token API ที่ `/api/token/` หรือการยิงสลิปที่ `/payment/slip/` ถูกจำกัดไว้ที่ **10 ครั้งต่อนาทีต่อ IP**
  2. หากส่งคำขอเกิน 10 ครั้งภายใน 1 นาที ระบบจะตอบกลับด้วยรหัส `HTTP 429 Too Many Requests` พร้อมข้อความแจ้งเตือน

## 5. การทำงานเบื้องหลัง (Under the Hood)

ส่วนนี้อธิบายตรรกะเชิงวิศวกรรมซอฟต์แวร์ที่ทำงานอยู่เบื้องหลัง โดยแปลงเป็นคำอธิบายที่เข้าใจง่าย:

### 5.1 สถาปัตยกรรมแบบแยก 4 ชั้น (4-Layer System Flow)

```
┌─────────────────────────────────────────────────────────────┐
│ 1. Presentation Layer (หน้าเว็บ Bootstrap 5 + Liquid Glass)   │
└──────────────────────────────┬──────────────────────────────┘
                               │ ส่ง HTTP Request / AJAX Form
┌──────────────────────────────▼──────────────────────────────┐
│ 2. Logic & Views Layer (Django CBV & REST ViewSets)         │
│    - ตรวจสอบสิทธิ์ (StaffRequiredMixin / Permissions)        │
│    - ตรวจ CSRF Token และดักจับ Method (ห้าม GET ลบข้อมูล)     │
└──────────────────────────────┬──────────────────────────────┘
                               │ ส่งต่อข้อมูลให้ Service
┌──────────────────────────────▼──────────────────────────────┐
│ 3. Business Service Layer (ศูนย์รวมตรรกะทางธุรกิจ 17 ตัว)       │
│    - PaymentService, OrderStatusService, Cart, SlipOK       │
│    - ไม่ขึ้นกับ HTTP รันซ้ำได้ผ่าน CLI / Unit Tests          │
└──────────────────────────────┬──────────────────────────────┘
                               │ อ่าน/เขียนผ่าน QuerySet & Manager
┌──────────────────────────────▼──────────────────────────────┐
│ 4. Data Access Layer (Django ORM Models & SQLite Database)  │
│    - 9 โมเดลหลัก พร้อมระบบความสัมพันธ์แบบ Cascade ที่รัดกุม    │
└─────────────────────────────────────────────────────────────┘
```

**ทำไมต้องมี Service Layer?**  
ในระบบทั่วไป โปรแกรมเมอร์มักเขียนโค้ดตรวจสอบเงินไว้ใน Controller หรือ View ทำให้เมื่อมีช่องทางชำระเงินใหม่ (เช่น สลิป, บัตร, QR, API) ตรรกะจะกระจัดกระจายและเกิดยอดเงินซ้ำ  
ระบบนี้แก้ปัญหาโดยให้ **View มีหน้าที่แค่รับค่าและส่งต่อ** ตรรกะการคิดเงินและเปลี่ยนสถานะทั้งหมดถูกย้ายมาอยู่ที่ `services.py` เพียงที่เดียว

---

### 5.2 จุดรับเงินจุดเดียว (Single Point of Entry)

```
[ สแกนสลิป OCR ] ──┐
[ สแกน QR โอนเงิน ] ──┼──► PaymentService.record_payment() ──► ตรวจสอบยอดรวม ──► ปรับสถานะเป็น "paid" อัตโนมัติ
[ ปุ่มโอน 1 คลิก ]  ──┘                                            │
                                                                   └──► บันทึก ActivityLog (Audit)
```

* ฟังก์ชัน `PaymentService.record_payment()` เป็น "ประตูบานเดียว" ที่เปิดรับเงินเข้าสู่ระบบ
* ทุกครั้งที่มีรายการแจ้งชำระ ฟังก์ชันนี้จะ:
  1. สร้างรายการในตาราง `Payment`
  2. รวมยอดชำระสะสมทั้งหมดของออเดอร์นั้น: $\sum \text{Payment.amount}$
  3. เปรียบเทียบกับยอดรวมของออเดอร์ (`order.total_amount`)
  4. หาก **ยอดชำระครบถ้วน** $\rightarrow$ อัปเดต `order.status = 'paid'` อัตโนมัติ
  5. บันทึกประวัติการเงินลงใน `ActivityLog` ทันที

---

### 5.3 บันไดสถานะคำสั่งซื้อทิศทางเดียว (One-Way State Ladder)

สถานะของคำสั่งซื้อถูกออกแบบเป็น **Finite State Machine (FSM)** ที่เดินหน้าได้ทางเดียว:

$$\text{รอชำระเงิน (pending)} \xrightarrow[\text{ยอดเงินครบ}]{\text{อัตโนมัติ}} \text{ชำระเงินแล้ว (paid)} \xrightarrow[\text{ส่งพัสดุ}]{\text{เจ้าหน้าที่}} \text{จัดส่งแล้ว (shipped)} \xrightarrow[\text{ได้รับของ}]{\text{ลูกค้ากดยืนยัน}} \text{ถึงมือแล้ว (delivered)}$$

* **กฎข้อที่ 1**: สถานะ `paid` ปรับด้วยมือไม่ได้ ต้องผ่าน `PaymentService`
* **กฎข้อที่ 2**: สถานะ `delivered` ให้ลูกค้าเป็นผู้ยืนยันเป็นหลัก
* **กฎข้อที่ 3 (Superuser Override)**: หากเกิดกรณีพิเศษ เช่น ลูกค้าจ่ายเงินสดหน้าร้าน หรือโอนผิดบัญชี เฉพาะผู้ดูแลระบบสูงสุด (`is_superuser`) เท่านั้นที่กดข้ามได้ โดยระบบจะบังคับให้พิมพ์เหตุผล และจะสร้าง record ในตาราง `Payment` ควบคู่กันเสมอ เพื่อให้ยอดเงินในบัญชีไม่คลาดเคลื่อน

---

### 5.4 ระบบประวัติการทำงานแบบ Diffing (Append-Only Audit Trail)

ระบบจะไม่ลบหรือแก้ไขประวัติเก่าเด็ดขาด (`Append-Only`) โดยใช้หลักการ **Diffing**:
1. ก่อนฟอร์มจะบันทึก ระบบอ่านค่าตั้งต้นจาก `form.initial`
2. เมื่อผู้ใช้กดบันทึก ระบบนำค่าใหม่จาก `form.cleaned_data` มาเปรียบเทียบ
3. ระบบจะสกัดเฉพาะ **ฟิลด์ที่มีการเปลี่ยนแปลงจริง** บันทึกเป็น JSON เช่น:
   ```json
   {
     "salary": {"old": 45000, "new": 50000},
     "department": {"old": "ขาย", "new": "การตลาด"}
   }
   ```
4. บันทึกควบคู่กับ **ชื่อผู้กระทำ, วันที่-เวลา, และที่อยู่ IP** ทำให้ตรวจสอบย้อนหลังได้ 100%

---

### 5.5 ระบบควบคุมการเคลื่อนไหว Liquid Glass & Motion Core

* **Single Source of Truth**: มีปุ่มสายฟ้า (⚡) มุมบนของหน้าจอสำหรับเปิด-ปิด เอฟเฟกต์การเคลื่อนไหว (Motion)
* **สถาปัตยกรรม Mod Loader (`FX.register`)**:
  * ตัวหลักคือ `motion-core.js` โหลดก่อนเสมอ
  * เอฟเฟกต์ย่อยแยกเป็นไฟล์อิสระ เช่น `fx-countup.js`, `fx-glass.js`, `fx-ripple.js`, `fx-reveal.js`
  * เมื่อปิด Motion ระบบจะปิดอนิเมชันทั้งหมดพร้อมกันโดยไม่กระทบต่อการทำงานของหน้าเว็บ

## 6. คำถามที่พบบ่อยและการแก้ปัญหา (FAQ & Troubleshooting)

### Q1: แก้ไขไฟล์ CSS หรือ JavaScript แล้วทำไมหน้าเว็บไม่เปลี่ยน?
**สาเหตุ**: โปรเจกต์มีการเก็บไฟล์ static ในโฟลเดอร์ `staticfiles/` สำหรับขึ้น Production และมีการทำแคชเวอร์ชัน (`STATIC_VERSION`)  
**วิธีแก้ไข**: ให้รันคำสั่ง 2 บรรทัดนี้ทุกครั้งที่แก้ไฟล์ CSS/JS:
```bash
python manage.py collectstatic --noinput
# จากนั้นกด Ctrl+C เพื่อ Restart คำสั่ง python manage.py runserver ใหม่
```

### Q2: ต้องการล้างข้อมูลทดสอบแล้วใส่ข้อมูลตัวอย่างใหม่หมดทำอย่างไร?
**วิธีแก้ไข**: รันคำสั่ง seed สองคำสั่งนี้ ข้อมูลจะกลับมาสวยงามพร้อมส่งงานทันที:
```bash
python manage.py seed_catalog
python manage.py seed_demo_data
```

### Q3: ต้องการสร้างเอกสารรายงาน PDF และ Word ส่งอาจารย์ใหม่ทำอย่างไร?
**วิธีแก้ไข**: รันคำสั่งสร้างรายงาน เอกสารจะดึงสถิติจริงจากโค้ดมาสร้างเป็นเล่มวิชาการให้ทันที:
```bash
python manage.py build_report
```
*ไฟล์เอกสารจะถูกสร้างไว้ที่โฟลเดอร์ `docs/รายงาน/`*
